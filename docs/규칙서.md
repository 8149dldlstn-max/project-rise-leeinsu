## 3. n-tier 계층 규칙 (책임을 섞지 않는다)

요청은 **Controller → Service → Repository** 한 방향으로만 흐른다. 계층을 건너뛰지 않는다.

| 계층 | 하는 일 (책임) | 하면 안 되는 것 |
|---|---|---|
| **Controller** | HTTP 입출구. DTO로 값 받기, `@CurrentUser` → DTO 병합(§7.1), 상태코드/응답 직렬화, Swagger 문서 | **비즈니스 로직 금지**, DB 직접 접근 금지 |
| **Service** | 비즈니스 규칙(계산·검증·조합·트랜잭션·**소유권 검증**) | **HTTP(req/res) 몰라야 함**, SQL 직접 금지 |
| **Repository** | DB 접근(저장·조회·**집계 SUM**)만 | 비즈니스 규칙 금지 |

- **Controller는 얇게, Service는 두껍게, Repository는 단순하게.**
- Service는 `Request`, `Response`, `res.json` 같은 HTTP 개념을 **몰라야** 한다(순수 로직).
- 집계(SUM·GROUP BY)는 Repository의 쿼리로, 집계 결과의 **조합·파생 계산**(남은예산·사용률)은 Service로.
- **소유권 검증은 서비스 계약의 공용 메서드로** 한 곳에 둔다. 예: `ITripService.getOwnedTrip(userId, tripId)` — 없으면 404, 남의 것이면 403. 다른 도메인 서비스(환율·지출…)도 이 메서드를 재사용한다.

## 4. 의존성 주입(DI) = 클래스 토큰 주입 (핵심 규칙)

**계약은 `interface/` 폴더의 abstract class에 둔다. Controller는 `IUserService`, Service는 `IUserRepository`에만 의존한다.** (DIP) 실제 구현은 module에서 연결.

> **왜 `interface`가 아니라 `abstract class`인가?** TypeScript `interface`는 컴파일하면 **런타임에 사라져서** DI 토큰이 못 된다.
> 그래서 계약을 **`abstract class`** 로 만들어 "타입 + 런타임 토큰"을 겸하게 한다. (폴더명 `interface/`·이름 `I…` 접두사는 그대로 유지 가능)

```ts
// interface/user.repository.interface.ts — 계약 = 토큰
export abstract class IUserRepository {
  abstract findByEmail(email: string): Promise<User | null>;
  abstract save(user: Partial<User>): Promise<User>;
}

// interface/user.service.interface.ts
export abstract class IUserService {
  abstract signup(createUserDto: CreateUserDto): Promise<User>;
}

// user.repository.ts — IUserRepository 구현(TypeORM)
@Injectable()
export class UserRepository extends IUserRepository {
  constructor(
    @InjectRepository(User) private readonly userRepository: Repository<User>,
  ) { super(); }
  findByEmail(email: string) { return this.userRepository.findOne({ where: { email } }); }
  save(user: Partial<User>) { return this.userRepository.save(user); }
}

// user.service.ts — IUserService 구현, IUserRepository만 사용(구현 모름)
@Injectable()
export class UserService extends IUserService {
  constructor(private readonly userRepository: IUserRepository) { super(); } // ← 타입으로 바로 주입
  signup(createUserDto: CreateUserDto) { /* ... */ return this.userRepository.save(/* ... */); }
}

// user.controller.ts — IUserService에 의존
@Controller('users')
export class UserController {
  constructor(private readonly userService: IUserService) {}
}

// user.module.ts — 토큰(abstract) ↔ 구현 연결
@Module({
  imports: [TypeOrmModule.forFeature([User])],
  controllers: [UserController],
  providers: [
    { provide: IUserService, useClass: UserService },
    { provide: IUserRepository, useClass: UserRepository },
  ],
  exports: [IUserService],
})
export class UserModule {}
```

- **주입은 타입으로 바로:** abstract class가 곧 토큰이라 `constructor(private x: IUserRepository)` 만으로 끝. (명시하려면 `@Inject(IUserRepository)` 도 가능)
- **문자열 토큰(`'USER_REPOSITORY'`) 금지** — 오타·타입안전성 문제. 항상 abstract class 토큰.
- **교체 한 줄:** 테스트 땐 module에서 `useClass: UserRepository` → `InMemoryUserRepository` 로만 바꾸면 됨(Service 불변).
- 모든 도메인이 이 패턴(`interface/` 계약 + 클래스 토큰)을 **반드시** 따른다.

## 4.5 configs 래퍼 모듈 — DB·설정을 한 번만 등록해 어디서나 (v1.1 재작성)

DB 연결과 환경설정은 **모듈마다 import하지 않는다.** `configs/` 폴더의 **래퍼 모듈**로 딱 한 번 등록하고, `app.module.ts`는 래퍼만 import한다.

```ts
// configs/config-wrapper.module.ts — 전역 설정 + 기동 시 .env 검증
@Module({
  imports: [
    ConfigModule.forRoot({
      envFilePath: '.env',
      isGlobal: true, // 어디서나 ConfigService 주입 가능
      validationSchema: Joi.object({
        NODE_ENV: Joi.string().valid('development', 'production', 'test').default('development'),
        APP_PORT: Joi.number().port().default(3000),
        DATABASE_HOST: Joi.string().required(),
        DATABASE_PORT: Joi.number().port().required(),
        DATABASE_NAME: Joi.string().required(),
        DATABASE_USERNAME: Joi.string().required(),
        DATABASE_PASSWORD: Joi.string().allow('').default(''),
        DATABASE_SYNCHRONIZE: Joi.boolean().default(false),
        DATABASE_SSL: Joi.boolean().default(false), // Supabase 등 관리형 Postgres = true
        JWT_SECRET: Joi.string().required(),
        JWT_ACCESS_EXPIRATION_SECONDS: Joi.number().integer().default(86400),
      }),
    }),
  ],
})
export class ConfigWrapperModule {}

// db/postgresql.options.ts — 연결 옵션 팩토리(연결 설정의 단일 출처)
export const createPostgresDataSourceOptions = (config: PostgresDataSourceConfig) => ({
  type: 'postgres' as const,
  host: config.host,
  port: Number(config.port),
  username: config.username,
  password: config.password,
  database: config.database,
  // 로컬 개발 전용 스위치 — 운영은 false + 마이그레이션 사용
  synchronize: config.synchronize ?? false,
  // Supabase 등 관리형 Postgres는 SSL 필요, 로컬은 false
  ssl: config.ssl ? { rejectUnauthorized: false } : false,
});

// configs/typeorm-wrapper.module.ts — DB 연결 등록(키는 반드시 ENV_KEYS로)
@Module({
  imports: [
    TypeOrmModule.forRootAsync({
      imports: [ConfigModule],
      inject: [ConfigService],
      useFactory: (configService: ConfigService) => ({
        ...createPostgresDataSourceOptions({
          host: configService.get<string>(ENV_KEYS.DATABASE_HOST),
          port: configService.get<number>(ENV_KEYS.DATABASE_PORT),
          username: configService.get<string>(ENV_KEYS.DATABASE_USERNAME),
          password: configService.get<string>(ENV_KEYS.DATABASE_PASSWORD),
          database: configService.get<string>(ENV_KEYS.DATABASE_NAME),
          synchronize: configService.get<boolean>(ENV_KEYS.DATABASE_SYNCHRONIZE),
          ssl: configService.get<boolean>(ENV_KEYS.DATABASE_SSL),
        }),
        autoLoadEntities: true,
      }),
    }),
  ],
})
export class TypeOrmWrapperModule {}

// app.module.ts — 래퍼 + 기능 모듈만 조립
@Module({
  imports: [
    ConfigWrapperModule,
    TypeOrmWrapperModule,
    TokenModule,          // §4.7
    AuthModule, UserModule, /* …다른 도메인 모듈 */
  ],
})
export class AppModule {}
```

- `.env` 키가 빠지면 **기동 자체가 실패**한다(Joi) — 배포에서 "환경변수 누락으로 이상 동작"을 원천 차단.
- 각 도메인 모듈은 **자기 엔티티만** `TypeOrmModule.forFeature([User])`로 등록(§4 참고).
- **비밀값(DB 접속정보·JWT 시크릿 등)은 `.env`** — 코드·커밋에 절대 넣지 않는다. `.gitignore`에 `.env` 필수, 대신 `.env.example` 커밋.

**`.env.example`은 “값이 빈” 템플릿이다 — 값을 채워 두지 않는다.**
키 목록과 형식 힌트만 두고, 실제 값(호스트·비번·시크릿)은 각자 `.env`에만. (샘플에 값이 박히면 그게 곧 유출)

```bash
# .env.example  — 커밋함 (값은 비움 / 형식만 주석으로)
NODE_ENV=
APP_PORT=
DATABASE_HOST=          # 예: aws-0-xxxx.pooler.supabase.com
DATABASE_PORT=          # 예: 5432
DATABASE_NAME=          # 예: postgres
DATABASE_USERNAME=      # 예: postgres.xxxxxxxx
DATABASE_PASSWORD=      # 프로젝트 생성 시 정한 비번
DATABASE_SYNCHRONIZE=   # 개발 true / 운영 false
DATABASE_SSL=           # Supabase true / 로컬 false
JWT_SECRET=             # 아무 긴 랜덤 문자열
JWT_ACCESS_EXPIRATION_SECONDS=
```

```bash
# .env  — 커밋 안 함(.gitignore). 실제 값은 여기에만.
DATABASE_HOST=aws-0-ap-northeast-2.pooler.supabase.com
DATABASE_PASSWORD=실제비번
JWT_SECRET=실제랜덤값
# …나머지 키도 실제 값으로
```

> Joi가 기동 시 검사하므로, `.env`의 빈 값/누락은 서버가 안 켜지며 바로 잡힌다.

## 4.6 상수 관리 — 하드코딩 금지 (v1.1 신설)

**env 키·에러 메시지·매직 넘버를 코드 여기저기에 문자열로 박지 않는다.** `common/constants/index.ts` 배럴 한 곳에 모은다.

```ts
// common/constants/index.ts
export enum ENV_KEYS {
  NODE_ENV = 'NODE_ENV',
  APP_PORT = 'APP_PORT',
  DATABASE_HOST = 'DATABASE_HOST',
  // …(.env의 모든 키)
  DATABASE_SSL = 'DATABASE_SSL',   // Supabase = true, 로컬 = false
  JWT_SECRET = 'JWT_SECRET',
  JWT_ACCESS_EXPIRATION_SECONDS = 'JWT_ACCESS_EXPIRATION_SECONDS',
}

export enum ERROR_MESSAGE {
  UNAUTHORIZED = '로그인이 필요합니다.',
  TOKEN_INVALID = '유효하지 않은 토큰입니다.',
  EMAIL_ALREADY_EXIST = '이미 가입된 이메일입니다.',
  EMAIL_PASSWORD_NOT_MATCH = '이메일 또는 비밀번호가 올바르지 않습니다.',
  TRIP_NOT_FOUND = '여행을 찾을 수 없습니다.',
  TRIP_FORBIDDEN = '본인의 여행만 접근할 수 있습니다.',
  // …(도메인 규칙 위반 메시지 전부)
}

export const PASSWORD_HASH_ROUNDS = 10;
export const BEARER_TOKEN_PREFIX = 'Bearer ';
```

**규칙 3줄:**
1. `configService.get('JWT_SECRET')` 처럼 **env 키를 문자열로 직접 쓰지 않는다** → `configService.get(ENV_KEYS.JWT_SECRET)`.
2. `throw new NotFoundException('여행을 찾을 수 없습니다.')` 처럼 **메시지를 서비스에 하드코딩하지 않는다** → `ERROR_MESSAGE.TRIP_NOT_FOUND`. (오타·중복·표현 불일치 방지, 프론트와 메시지 계약 一元화)
3. 해시 라운드·기본 통화 같은 **매직 값도 이름 붙은 상수**로.

## 4.7 토큰 서비스 — JWT 발급·검증 전담 분리 (v1.1 신설)

JWT의 비밀키·만료시간·서명·검증을 **auth 모듈이나 가드에 흩뿌리지 않는다.** `common/utils/token/`의 **전역 TokenService** 한 곳이 전담한다.

```ts
// common/utils/token/token.service.ts
@Injectable()
export class TokenService {
  private readonly secret: string;
  private readonly accessTokenExpirationSeconds: number;

  constructor(
    private readonly configService: ConfigService,
    private readonly jwtService: JwtService,
  ) {
    this.secret = this.configService.get<string>(ENV_KEYS.JWT_SECRET)!;
    this.accessTokenExpirationSeconds = Number(
      this.configService.get<string>(ENV_KEYS.JWT_ACCESS_EXPIRATION_SECONDS),
    );
  }

  signAccessToken(authenticatedUser: AuthenticatedUser): Promise<string> {
    return this.jwtService.signAsync(
      { id: authenticatedUser.id, email: authenticatedUser.email },
      { secret: this.secret, expiresIn: this.accessTokenExpirationSeconds },
    );
  }

  /** 검증 실패(만료·위조)는 null 반환 — 예외 변환은 호출부(가드)의 책임 */
  async verifyAccessToken(token: string): Promise<AuthenticatedUser | null> {
    try {
      return await this.jwtService.verifyAsync<AuthenticatedUser>(token, { secret: this.secret });
    } catch {
      return null;
    }
  }
}

// common/utils/token/token.module.ts
@Global()
@Module({
  imports: [JwtModule.register({})], // 옵션은 TokenService가 서명 시점에 명시
  providers: [TokenService],
  exports: [TokenService],
})
export class TokenModule {}
```

- **AuthService**는 로그인 성공 시 `tokenService.signAccessToken(...)`을 호출할 뿐, secret·만료를 모른다.
- **JwtAuthGuard**는 헤더 파싱 + `tokenService.verifyAccessToken(...)` 위임 + 401 변환만 한다.
- auth.module에서 `JwtModule.registerAsync(...)`로 secret을 등록하는 방식은 **쓰지 않는다** (설정이 모듈 등록부에 숨고, 다른 모듈에서 재사용이 안 됨).
- 만료시간은 **초 단위 숫자**(`JWT_ACCESS_EXPIRATION_SECONDS=86400`)로 관리한다 — `'1d'` 같은 문자열은 타입이 안 맞아 캐스팅 꼼수가 필요해진다.

## 5. SOLID 5원칙 — 이 프로젝트에서의 의미

| 원칙 | 이 프로젝트에서 | 예 |
|---|---|---|
| **S** 단일책임 | 한 클래스는 한 가지 이유로만 바뀐다 | Controller=입출구, Service=규칙, Repository=저장, TokenService=토큰. 섞지 않음 |
| **O** 개방·폐쇄 | 확장은 열고, 수정은 닫는다 | 새 저장방식 추가 시 새 Repository 구현만, Service 수정 X |
| **L** 리스코프 치환 | 구현은 추상 계약을 어기지 않는다 | `InMemory`·`TypeOrm` Repository 어느 것이든 Service가 동일 동작 |
| **I** 인터페이스 분리 | 안 쓰는 메서드에 의존시키지 않는다 | Repository엔 그 도메인이 실제 쓰는 메서드만 |
| **D** 의존성 역전 | 상위(Service)가 하위(구현)에 직접 의존 X | §4 클래스 토큰 DI 그 자체 |

> **한 줄 원칙:** "바뀔 이유가 다른 것은 다른 클래스로, 의존은 추상에."

## 6. 정규화 원칙 + 트레이드오프 (역정규화 허용 기준)

**기본값 = 정규화(3NF) 지향.** 단, **기능/성능상 근거가 있으면 역정규화 허용** — 반드시 **주석으로 이유**를 남긴다.

**지킨다 (정규화)**
- **1NF:** 한 칸에 값 하나. 콤마로 여러 개 넣지 않는다(`tags: "a,b,c"` 금지 → 별도 테이블).
- **2NF/3NF:** 딸린 속성(이행 종속) 분리. 예: 지역 코드→지역명을 매 행에 복제하지 않음.
- **M:N은 중간테이블:** 참가(Participation)·관심(UserInterest)·배정(Assignment)처럼 연결은 별도 테이블 + `UNIQUE(a,b)`.

**허용한다 (역정규화 — 이유 주석 필수)**
- **스냅샷(과거 불변):** `Expense.krwAmount`·`exchangeRate` 저장 → 나중에 환율이 바뀌어도 **과거 지출은 변하면 안 되므로** 계산값을 박아둔다.
- **계산 캐시:** 조회가 잦고 자주 안 바뀌는 집계(예: 참가자 수)는 저장 가능 — **단 "누가 언제 갱신하는지" 명시**.

**금지한다**
- 근거 없는 중복, 갱신 이상(update anomaly)을 부르는 복제(한 값 바꾸려 여러 행 고쳐야 하는 구조).

> **판단 문장:** "정규화가 기본. 역정규화는 **이유를 주석으로 댈 수 있을 때만.** 못 대면 정규화로 되돌린다." (강사 판단가이드와 동일 기준)

## 7. DTO & 검증 (입력은 반드시 DTO로)

- **입력은 전부 DTO 클래스** + `class-validator` 데코레이터. Controller가 raw body를 직접 만지지 않는다.
- `main.ts`에 **전역 ValidationPipe**(`whitelist: true` — DTO에 없는 필드 제거, `transform: true`).
- 생성/수정 분리: `CreateXxxDto`, `UpdateXxxDto`(= `PartialType(CreateXxxDto)`).
- **DTO에 비즈니스 로직 금지** — DTO는 필드 선언·검증 데코레이터만. 매핑·계산은 Service의 몫.

```ts
// create-user.dto.ts
export class CreateUserDto {
  @ApiProperty({ example: 'kim@ex.com' })
  @IsEmail() email: string;

  @ApiProperty({ minLength: 6 })
  @IsString() @MinLength(6) password: string;

  @ApiProperty({ required: false })
  @IsOptional() @IsString() nickname?: string;
}
// main.ts
app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));
```

## 7.1 로그인 사용자 식별자(userId) 주입 패턴 (v1.1 신설)

**userId는 클라이언트가 body로 보내는 값이 아니다.** 가드가 검증한 토큰에서 나온 값만 믿는다. 전달 방법은 엔드포인트 종류에 따라 둘로 고정한다.

**① body가 있는 엔드포인트(POST/PATCH): DTO에 병합해서 서비스에 DTO 하나로**

```ts
// dto — userId를 "선언만" 한다: 검증 데코레이터·@ApiProperty를 붙이지 않는다
export class CreateTripDto {
  @ApiProperty() @IsString() title: string;
  /* …클라이언트 입력 필드들… */

  // 클라이언트 입력이 아니라 컨트롤러가 @CurrentUser로 주입.
  // 검증 데코레이터가 없어 whitelist가 클라이언트가 보낸 값은 제거한다.
  userId: number;
}

// controller — @CurrentUser에서 꺼내 DTO에 병합, 서비스엔 DTO 하나만
@Post()
create(
  @CurrentUser() currentUser: AuthenticatedUser,
  @Body() createTripDto: CreateTripDto,
): Promise<Trip> {
  createTripDto.userId = currentUser.id;
  return this.tripService.create(createTripDto);
}

// service — 매개변수를 늘리지 않고 dto.userId를 쓴다
create(createTripDto: CreateTripDto): Promise<Trip> { /* createTripDto.userId 사용 */ }
```

**② body가 없는 엔드포인트(GET/DELETE): 프리미티브 매개변수로**

```ts
@Delete(':tripId')
remove(
  @CurrentUser() currentUser: AuthenticatedUser,
  @Param('tripId', ParseIntPipe) tripId: number,
): Promise<void> {
  return this.tripService.remove(currentUser.id, tripId);
}
```

**이 패턴이 지켜주는 것 3가지:**
1. **스푸핑 차단** — 클라이언트가 body에 `"userId": 999`를 넣어도 whitelist가 제거한다(검증 데코레이터가 없는 필드라서). 저장되는 건 항상 토큰의 주인.
2. **Swagger 청결** — @ApiProperty가 없으니 문서에 userId가 노출되지 않는다.
3. **서비스 시그니처 단순화** — `create(userId, tripId, dto)` 처럼 매개변수가 늘어지지 않는다.

> `UpdateXxxDto extends PartialType(CreateXxxDto)`를 쓰면 userId가 optional이 되므로, Update DTO에서 `userId: number`를 **다시 필수로 재선언**한다.

## 8. 인증 & 가드

- **회원가입:** password는 **bcryptjs 해시**로 저장(평문 금지, 라운드는 상수 `PASSWORD_HASH_ROUNDS`). 응답에 password **절대 미포함**.
  - ⚠️ 네이티브 `bcrypt`는 Windows에서 빌드 도구가 없으면 설치가 실패한다 → **순수 JS `bcryptjs`** 사용: `import * as bcrypt from 'bcryptjs'` (API 동일: `hash`·`compare`). 패키지: `bcryptjs` + `@types/bcryptjs`.
- **로그인:** 성공 시 **JWT access token** 발급(발급은 §4.7 TokenService). 이후 요청은 `Authorization: Bearer <token>`.
- **JwtAuthGuard:** 토큰 없거나 틀리면 **401** — 검증은 TokenService에 위임, 가드는 헤더 파싱과 401 변환만.
- **RolesGuard + `@Roles('TRAINER')`:** 권한 없으면 **403**. (최은수 강사전용, 박종규 관장전용 등)
- 가드는 `common/guards/`에 두고 컨트롤러/메서드에 `@UseGuards(...)`로 부착.
- **소유권 검증(역할과 별개):** 리소스에 주인이 있으면 — 없으면 **404**, 남의 것이면 **403**. 소유권 검증 메서드는 그 도메인 서비스 계약에 공용으로 두고(§3), 자식 도메인들이 재사용한다.

```ts
@UseGuards(JwtAuthGuard, RolesGuard)
@Roles('TRAINER')
@Post('homeworks')
create(@CurrentUser() currentUser: AuthenticatedUser, @Body() createHomeworkDto: CreateHomeworkDto) { ... }
```

## 9. 에러 처리 & 응답 규칙

- 예외는 **NestJS HttpException** 계열로: `NotFoundException`(404), `BadRequestException`(400), `ForbiddenException`(403), `UnauthorizedException`(401), `ConflictException`(409, 중복).
- **메시지는 전부 `ERROR_MESSAGE` 상수로**(§4.6) — 하드코딩 금지.
- Service에서 도메인 규칙 위반 시 적절한 예외를 던지고, Controller는 그대로 전파(try/catch 남발 금지).
- 성공 상태코드: 생성=**201**, 조회/수정=**200**, 삭제=**200/204**.
- 응답 형태 통일: 리소스 객체(또는 배열) 반환. 민감필드(password 등) 제거 후 반환.
